# 短剧分镜制作助手：产品需求文档（PRD）

> 状态：需求方向已确认，产品方案待评审
>
> 本文档是后续设计和开发的唯一产品基线。现有 `src/` 实现属于冻结的技术 Spike，不代表本文档已经全部实现。
>
> 最后更新：2026-08-29

## 1. 产品概述

短剧分镜制作助手面向短剧前期制作人员，帮助用户将一集已经完成的剧本转换为可理解、可编辑、可检查、可导出的生产资料。

核心链路：

```text
一集剧本
  → 故事资产
  → 场次
  → 分镜卡片
  → Image / Video Prompt
  → 连续性问题
  → 修改与版本
  → 完整生产包
```

产品不是：

- 自动创作完整长剧本的编剧机器人；
- 真实图像或视频生成平台；
- 多人审批系统；
- 传统表格型分镜管理系统；
- 面向观众的内容产品。

## 2. 目标用户

### 2.1 第一阶段用户

第一阶段按**个人操作者**设计，用户可能承担以下任一工作：

- 编剧助理：整理剧本、检查人物和场景；
- 导演或分镜师：设计场次、镜头和 Prompt；
- 项目负责人：查看生产总览、问题和导出资料。

第一阶段不实现用户登录、成员管理、角色权限和多人实时协作。服务器访问默认直接进入工作区，后续可在 API 前增加认证层。

### 2.2 用户已有材料

用户通常拥有：

- 一集相对完整的短剧剧本；
- Markdown 或纯文本格式；
- 可选的后续补充说明。

第一版输入方式：

- 粘贴文本；
- 上传 `.md` 或 `.txt` 文件。

## 3. 核心问题

短剧制作人员目前需要手工完成以下工作：

1. 从剧本中整理角色、场景、道具和时间线；
2. 把文本拆成场次和镜头；
3. 为镜头补齐景别、构图、动作、运镜和时长；
4. 编写图像和视频生成 Prompt；
5. 检查角色、道具、场景和动作在多个镜头之间是否连续；
6. 修改后重新整理受影响镜头；
7. 把结果整理为可交接的生产包。

产品要减少这些重复性工作，同时让用户始终可以看到和修改结构化资产。

## 4. 产品目标

### 4.1 第一阶段目标

用户可以：

1. 打开服务器地址；
2. 粘贴或上传一集剧本；
3. 启动自动生成流程；
4. 实时查看各阶段进度；
5. 查看故事资产、场次、分镜卡片和问题；
6. 直接编辑故事资产、分镜制作字段和 Prompt；
7. 修改故事资产后自动重生成受影响的场次和镜头；
8. 对失败项单独重试；
9. 忽略不影响使用的问题；
10. 导出完整生产包。

### 4.2 成功标准

- 一集已完成剧本可以创建一个可追踪的生产任务；
- 任务能够自动生成结构化故事资产、场次和分镜；
- 生成过程可以实时查看；
- 单个场次或镜头失败不会导致整集结果丢失；
- 用户可以定位问题到具体资产或镜头；
- 用户的修改不会覆盖旧版本；
- 修改故事资产能够计算影响范围并触发受影响内容重生成；
- 导出内容可供后续制作人员使用；
- 页面不要求用户理解 Agent、Workflow、Schema 或数据库概念。

## 5. 第一阶段范围

### 5.1 剧本导入

- 新建一次制作任务；
- 输入项目名称；
- 输入第几集；
- 粘贴剧本；
- 上传 `.md` / `.txt`；
- 保存原始文本；
- 保存导入时间和来源文件名；
- 创建不可覆盖的 ScriptVersion。

### 5.2 故事资产

系统从剧本中生成：

- 故事摘要；
- 角色卡；
- 场景卡；
- 道具卡；
- 人物关系；
- 剧情事件；
- 时间线；
- 场次列表；
- 来源、置信度和问题标记。

用户可以编辑故事资产。编辑后系统需要：

```text
保存新版本
  → 计算影响范围
  → 自动重新生成受影响内容
  → 保留旧版本和变更说明
```

### 5.3 分镜生产

每张分镜卡包含：

- 场次编号；
- 镜头编号；
- 画面摘要；
- 人物/主体；
- 动作；
- 景别；
- 构图；
- 运镜；
- 时长；
- 光线；
- 情绪；
- Image Prompt；
- Video Prompt；
- 来源和版本；
- 连续性问题；
- 生成状态。

第一版不使用传统分镜表格作为主界面。

### 5.4 审查和问题

系统自动检查：

- 角色外观和身份连续性；
- 场景空间连续性；
- 道具状态连续性；
- 时间线和光线；
- 动作因果和物理逻辑；
- 对白与动作一致性；
- 镜头语言完整性；
- Prompt 是否足够具体。

问题处理原则：

- 默认不中断整体任务；
- 集中显示问题；
- 支持定位到相关资产；
- 支持自动修订低风险问题；
- 支持单项重试；
- 用户可以忽略问题后导出；
- 导出时必须记录被忽略的问题。

### 5.5 编辑和版本

可直接编辑：

- 故事资产字段；
- 分镜制作字段；
- Image Prompt；
- Video Prompt。

每次修改保留：

- 修改前内容；
- 修改后内容；
- 修改时间；
- 修改来源；
- 修改原因；
- 影响范围；
- 自动重生成结果。

### 5.6 导出

完整生产包包含：

```text
original-script.md
story-bible.md
scenes.md
storyboard.md
prompts.json
reviews.json
issues.json
versions.json
manifest.json
```

导出不因普通未处理问题被阻断。导出清单需要说明：

- 当前版本；
- 生成时间；
- 使用的模型模式；
- 已自动修订数量；
- 失败项；
- 被忽略的问题；
- 未完成或不可用的资产。

## 6. 主要用户流程

```text
进入首页
  → 粘贴或上传剧本
  → 开始生成
  → 查看实时进度
  → 查看制作总览
  → 查看故事资产和分镜卡片
  → 修改或重试
  → 查看问题和版本
  → 导出完整生产包
```

## 7. 明确不做

第一阶段不做：

- 登录、注册、邀请和权限；
- 正式审批角色和审批流；
- 多人实时协作；
- 真实图像生成；
- 真实视频生成；
- 配音、字幕和剪辑；
- 发布平台对接；
- 多租户；
- 多集跨集连续性；
- 图数据库；
- MCP 插件市场。

## 8. 非功能需求

### 易用性

- 首次进入页面后可以直接开始导入；
- 不要求用户理解技术术语；
- 每个阶段显示当前状态和下一步；
- 失败信息必须包含可执行的处理建议。

### 可追踪性

- 所有任务有唯一 ID；
- 所有资产有版本；
- 所有自动生成结果记录来源和模型模式；
- 所有修改记录影响范围。

### 可靠性

- 单镜失败隔离；
- 任务状态持久化；
- 页面刷新后可以恢复任务和资产；
- 服务器重启后不丢失业务数据；
- 导出失败不破坏已有资产。

### 部署

- 使用 Docker 部署到服务器；
- PostgreSQL 保存业务数据；
- 独立 Worker 执行长任务；
- 文件存储通过抽象接口实现，第一版默认服务器本地磁盘；
- Mock 和 Real 模型可以通过配置切换。

## 9. 验收原则

后续实现必须以本文档和 `traceability-matrix.md` 为准。代码存在、单元测试通过或 API 返回成功，都不能单独视为产品需求完成；必须同时有页面、流程和验收证据。
