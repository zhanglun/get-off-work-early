## 1. 当前最重要的规则

**不要在产品方案评审完成前继续写业务代码。**

之前曾经发生过：在没有充分确认需求、用户操作流程和产品形态之前，直接实现后端 Workflow、Repository 和 API。后续用户明确指出这不符合预期。因此本文件以及 `docs/prd.md` 等方案文档优先于现有代码。

下一次会话的正确开场：

1. 先读取本文件；
2. 再读取 `docs/prd.md`、`docs/user-flows.md`、`docs/information-architecture.md`、`docs/architecture.md`；
3. 向用户总结当前已确认决策和仍待评审的问题；
4. 询问用户是否确认方案，或需要修改哪部分；
5. 在用户明确确认产品方案前，不实现业务功能、不重构现有 Spike。

## 2. 已确认的产品方向

产品暂定名称：**短剧分镜制作助手**。

核心价值：

```text
一集已完成剧本
  → 结构化故事资产
  → 场次
  → 分镜卡片
  → Image / Video Prompt
  → 连续性问题
  → 编辑和版本
  → 完整生产包
```

核心价值优先级：

1. 剧本结构化；
2. 分镜生产。

输入材料：一集已经完成的剧本。

输入方式：

- 粘贴文本；
- 上传 `.md` / `.txt` 文件。

主要用户：混合团队中的编剧助理、导演/分镜师、项目负责人；但是第一阶段按**个人操作者**设计，不做多人实时协作。

默认用户流程（对话形态 v2）：

```text
打开产品：第一屏是一个输入框
  → 粘贴或上传一集剧本
  → 补齐项目名称和集数，发送
  → 对话内活动流实时滚动（解析→资产→场次→分镜→检查）
  → 工件实时长出来（资产组/场次组/分镜卡）
  → 完成：制作摘要 + 问题汇总 + 生产包工件
  → 打字修改（"把林小雨的风衣改成深灰大衣"）
  → 影响分析 + 自动重生成 + 新版本工件
  → 对失败项打字重试或忽略问题
  → 一键导出完整生产包
```

## 3. 已确认的交互决策

| 决策 | 结果 |
|---|---|
| 产品形态 | **对话即产品**（Codex/DeepSeek 式）：输入框 + 活动流 + 内联工件，2026-08-30 脑爆确认 |
| 首页 | 第一屏是居中输入框邀请粘贴剧本，无仪表盘无页签 |
| 生成方式 | 自动连续生成 |
| 中间审批 | 不做正式审批环节，也不设置强制确认节点 |
| 生成进度 | 对话内活动流实时可见，可折叠、终态收敛；无独立进度页 |
| 结果呈现 | 对话内工件 + 制作摘要，无独立总览页 |
| 失败处理 | 不中断整体流程，标记问题并提供重试 |
| 主产物 | 故事资产 + 分镜生产包 + 项目资料 |
| 分镜 UI | 分镜卡片（对话内联工件，按场次分组可折叠），不做表格 |
| 分镜卡内容 | 制作信息 + Image/Video Prompt |
| 故事资产 | 用户可以直接编辑（打字优先，点卡片兜底） |
| 分镜可编辑字段 | 制作字段 + Image/Video Prompt |
| 故事资产修改影响 | 自动识别影响范围，自动重生成受影响内容 |
| 问题处理 | 继续生成并集中为问题汇总工件；用户可以忽略后导出 |
| 修订边界 | 自动修订只动措辞/格式，事实内容只标记（G1A） |
| 重生成执行 | 全自动后台执行，进度可见可取消（G2A） |
| 验收时长 | Mock 全链路 ≤ 2 分钟硬指标（G3A） |
| 聊天 | 对话即产品：主对话是唯一入口（2026-08-30 推翻原"右侧辅助助手"决策） |
| 图像/视频 | 第一版只生成 Prompt，不真实调用图像/视频服务 |
| 用户体系 | 暂不做登录、注册、权限、成员管理和多租户 |
| 部署 | 部署到服务器，不只在本机运行 |
| 文件存储 | 目标方案默认服务器本地磁盘，保留 Storage Adapter |
| 模型 | 目标方案支持 Mock 默认、Real 可切换 |
| 导出 | 一键整包，锁定 9 文件（Q2A/G4A） |
| 现有代码 | 冻结为 Spike，方案确认后再决定复用、重构或淘汰 |

## 4. 第一版范围

需要实现：

- 剧本粘贴和 `.md` / `.txt` 上传；
- Project / Episode / ScriptVersion；
- 故事资产：角色、场景、道具、关系、时间线和剧情事件；
- 场次生成；
- 分镜卡片；
- Image Prompt / Video Prompt；
- 连续性问题中心；
- 低风险自动修订；
- 单项失败隔离和重试；
- 故事资产编辑；
- 分镜制作字段和 Prompt 编辑；
- 影响范围分析；
- 受影响内容自动重生成；
- 版本和 before/after diff；
- 右侧聊天辅助；
- 实时任务进度；
- 完整 Markdown / JSON 生产包导出；
- Docker 服务器部署；
- API 和 Worker 分离；
- PostgreSQL 业务持久化；
- Runtime Storage 和业务数据分离。

明确不做：

- 登录、注册、邀请和权限角色；
- 正式审批流程；
- 多人实时协作；
- 真实图像生成；
- 真实视频生成；
- 配音、字幕、剪辑和发布；
- 多租户；
- 多集跨集连续性；
- 图数据库；
- MCP 插件市场。

## 6. 现有代码真实定位

`mastra-short-drama-agent/src/` 目前是此前实现的技术 Spike，曾经验证过：

- Markdown Parser；
- StoryBible/Scene/Shot 基础模型；
- Prompt/Review/Refine；
- PostgreSQL + Prisma；
- 基础 API；
- Mock 全链路；
- 基础导出；
- 最小演示页面。

这些能力不能直接视为新产品已经完成。特别是以下内容仍需要按新方案重构：

- 测试面板式页面 → 真正的制作工作区；
- 强制 StoryBible/Scene 确认 → 自动连续流程；
- 进程内异步执行和内存 Job Map → 服务器 API + Worker + 可恢复任务；
- 故事资产编辑和影响范围自动重生成；
- 文件上传；
- 实时进度；
- 问题中心；
- 版本页面；
- 完整生产包下载；
- 卡片内编辑；
- 需求到页面/API/测试的完整验收。

不要因为现有测试通过，就声称产品方案已经落地。

## 7. 代码复用原则

方案评审确认后，再逐项审查：

```text
现有 Spike
  ├── 复用：Parser、Schema、部分 Agent、部分 Repository
  ├── 重构：API、Workflow、任务系统、页面、编辑和影响分析
  └── 淘汰：不符合自动连续流程的确认门槛和测试面板交互
```

不要删除既有学习成果；`agent-base/` 保留为历史基线；`mastra-playground/` 只用于 Mastra 通用学习。

## 9. 验收要求

最终不能只运行后端测试。必须验证：

- 用户从首页能看懂并完成导入；
- 用户不需要理解技术术语；
- 页面能看到真实生成进度；
- 资产以卡片展示而不是原始 JSON；
- 修改故事资产能看到影响范围并触发重生成；
- 单项失败能重试；
- 问题可以定位、处理、忽略并在导出中记录；
- 版本和 diff 可查看；
- 服务器部署后数据和任务可恢复；
- 文档、页面、API、Workflow、数据库和测试相互对应。
