# Workflow vs Agent：方案对比与演进决策

> 状态：已决策（workflow 先行，2026-08-16）；待确认项见 §7
> 决策原则：**先解决业务问题，不为做 agent 而做 agent。agent 是手段，不是目的。**
> 关联文档：架构见 [`architecture.md`](./architecture.md) · 需求见 [`requirements.md`](./requirements.md) · 团队分工见 [`team-review.md`](./team-review.md)
> 本文档是**工程决策文档**，不是概念科普。核心问题是：什么条件下从 workflow 切到 agent。

---

## 0. 一句话结论

**v1 按 workflow 实现（盲测赢是靶心），agent 化作为可降级、可验证的演进方向，不预建、不提前。** 切换必须有触发条件（§6），无触发条件则维持 workflow。

## 1. 决策背景

- 2026-08-15/16 三轮 grilling 已定：范围 = 周五客户内测盲测打分，对比赢 = 成功。
- 讨论中出现的张力：**「做 agent」 vs 「解决业务问题」**。结论：周五的成败指标是盲测胜率，不是自主性；agent 化的价值在长尾扩展能力，不在单点输出质量。
- 老板预期「加 agent 更好」目前是**猜测**，未与老板对齐（§7）。

## 2. 需求拆解：两类目标必须分开

| 目标 | 指标 | 谁能满足 |
|---|---|---|
| 业务目标 | 盲测胜率（new vs old 对比赢） | workflow 足够，工具调用不直接贡献胜率 |
| 展示目标 | demo 体现「智能化 / 自主性」 | workflow 展示不足，需最小工具支线 |

**推论**：工具支线的定位是「demo 能力展示」，不是「成效手段」。它不能变成周五主链路的成败项。

## 3. 方案 A：Workflow（v1 执行方案，现状）

### 流程（已冻结，见 architecture.md §6）

```
POST /tasks → 任务中心建档 → BullMQ 入队
→ LegacyImporter 旧切分导入（落 OldShot=盲测基线）
→ 每镜 Shot Loop：Director → Reviewer → Refiner（固定 ≤3 轮，通过即停）
→ 落库 + 进度回写 → 盲测打分（pairs/scores）
```

### 技术方案（现有栈）

NestJS + BullMQ + Prisma/PostgreSQL + zod + OpenAI 兼容 LLM 封装（mock/real 双模式）。
**不用 LangGraph**：loop 是直线循环，手写 20 行；框架负资产（决策已沉淀在 team-review.md FAQ）。

### 核心原理

**确定性编排**：LLM 是「函数」——输入上下文，输出经 zod 校验的结构。控制流（顺序、轮数、熔断）全部由代码决定，LLM 不参与决策。核心保障：通过即停、≤3 轮熔断、单镜失败隔离（p-limit + try/catch per shot）、所有 LLM 输出过 zod（脏数据不进下一环）。

### 能力边界

- **能做**：单任务管线、结构化输出、自纠错循环、盲测对比、全链路留痕（rationale + reviewLog）。
- **不能做**：LLM 自主决策下一步、工具选择、跨任务记忆、多任务类型扩展（新任务 = 新管线）。

### 风险

- demo 展示性弱：自主性不可见，懂行的老板问「LLM 在哪一步自己做了决定」答不上来。
- 长尾能力弱：未来新任务类型需要重写管线，无法复用 loop。

## 4. 方案 B：Agent 智能化（演进方向，不预建）

### 流程（目标形态）

```
POST /tasks → 入队 → 导入 → 每镜 Agent 循环：
   LLM 决策（自评/选动作）→ 动作A：调工具（查角色卡/历史高分镜头/模板）→ 观察结果 → 继续
                        → 动作B：生成/改写 → 自评 → 通过即停（动态轮数）
→ 落库 + 进度回写 → 盲测打分
```

### 技术方案（在现有栈上的增量）

| 增量 | 说明 | 现状支撑 |
|---|---|---|
| function calling 通道 | `LlmService` 支持 tools 参数 + 多轮消息累积 | **硬伤：当前是无状态单发**（见下） |
| ToolRegistry | 只读检索工具注册：角色卡 / 历史高分镜头 / 模板 | Score、CharacterCard 表已存在；模板待队友 C 接口 |
| 动态轮数 | Reviewer confidence 驱动轮数 | `ReviewReportSchema.confidence` 钩子已留 |
| 降级开关 | `TOOL_MODE = off/mock/real`，端点不支持即回退 | 沿用 mock 先行模式 |
| 阶段 2 可选 | LangGraph 对照实验（Lesson 08，仅对照不作主实现）、跨集记忆存储 | 需评估向量库 vs 关系表 |

### 核心原理

**ReAct 循环**：推理（Reason）→ 行动（Act，调用工具）→ 观察（Observe，拿工具结果）→ 再推理。LLM 是「决策者」，工具是手的延伸，控制流由 LLM 自主推进而非代码硬编码。

### 依赖（新增，未齐备）

1. LLM 端点 **function calling 支持——未验证**（周一端点到手先验，这是硬前提）。
2. 模板接口（队友 C，接口文档未到）。
3. 记忆存储（跨集长期记忆，v1 明确出界，需新建评估）。
4. 工具执行环境：建议**只读工具**，不做写操作（写操作需要沙箱/权限设计，超出周五）。

### 风险

- **行为不可预测**：LLM 自主决策 → 质量/延迟/成本方差大，周五演示可能翻车。
- **调试与测试成本高**：非确定性输出，单测和 e2e 难写（现有 13/13 + 14/14 的确定性会损失）。
- **token 成本上升**：多轮 × 多镜 × 多集，量化后才能接（一集已约数百次调用）。

## 5. 对比总表

| 维度 | A：Workflow | B：Agent |
|---|---|---|
| 编排方式 | 代码硬编码顺序/轮数 | LLM 自主决策下一步 |
| LLM 角色 | 函数（入→出结构） | 决策者（选动作+调用工具） |
| 流程 | 直线循环，≤3 轮熔断 | 动态循环，轮数由 confidence 决定 |
| 可控性 | 高（每步代码可见） | 低（行为不可预测） |
| 可调试性 | 高（确定性 + 留痕） | 低（非确定性） |
| token 成本 | 可控（每镜 ≤6 次：Director 1 + Reviewer ≤3 + Refiner ≤2；多数 1-2 轮即停） | 上升（多轮 × 工具往返） |
| 延迟 | 稳定可预估 | 方差大 |
| 测试性 | 13/13 单测 + 14/14 e2e（现有） | 需要 mock 工具 + 降级测试 |
| 对业务指标贡献 | 直接（prompt 质量=胜率） | 间接（无直接证据提升输出质量） |
| demo 展示性 | 弱（自主性不可见） | 强（可演示自主查证） |
| 演进扩展性 | 弱（新任务=新管线） | 强（工具注册即能力扩展） |
| 周五风险 | 低（链路已验证） | 高（新链路未验证） |

## 6. 演进路径与触发条件（本文档的核心）

```
阶段 0（周五）  workflow 主链路 + 可选工具支线（TOOL_MODE=off 默认，不增加主链路风险）
阶段 1（demo 后） 工具接入 real（端点验证后）· 动态轮数 · 模板工具
阶段 2（长期）   跨集记忆 · LLM 自选动作 · Parser 恢复 · LangGraph 对照
```

**触发条件（满足任一才推进阶段 1，否则维持 workflow）：**

1. LLM 端点验证 function calling 可用（硬前提，周一验证）；
2. 出现 workflow 无法覆盖的需求（新任务类型 / 需要动态决策的环节）；
3. 老板/客户对「自主性」有明确**硬性要求**（区别于「可能更好」的猜测）；
4. 有业务指标证据表明 agent 化带来增益（如：动态轮数显著减少 needs_review 率）。

**回退条件**：工具支线导致主链路不稳定 → 立即 `TOOL_MODE=off`，主链路零影响（这是降级设计的价值）。

## 8. 老板对齐要点（价值翻译）

- **不讲概念，讲能力**：不讲「我做了个 agent」，讲「系统能自主查证、自检自纠、过程可审计」。
- **workflow 能承诺**：结果稳定、可审计、成本可控、周五可交付。
- **agent 化能承诺**：未来新任务不必重写管线（诚实前提：短期不提升输出质量）。
- **demo 展示口径建议**：「自检自纠 + 自主查证」比「我做了个 agent」更可信、更经得起追问。
